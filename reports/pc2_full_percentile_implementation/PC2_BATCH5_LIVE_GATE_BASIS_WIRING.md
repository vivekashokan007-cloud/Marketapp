# PC2 Batch5 Live Gate Basis Wiring

Date: 2026-08-09

## Objective

Wire calibrated percentile context into live Kind B candidate gates without changing Kind A safety floors and without adding any Supabase read/write load to live polling.

## Scope Implemented

- Added `PC2_GATE_BASIS_VERSION = pc2_gate_basis_v1`.
- Added live calibration metadata in `brain.py` for:
  - `MIN_CREDIT_RATIO`
  - `IV_RICH_MIN`
  - `MIN_PROB`
  - `MIN_SIGMA_OTM`
  - `MAX_SIGMA_OTM`
- Included `IV_RICH_MIN` as a live percentile candidate, per owner instruction and Claude clarification.
- Preserved Kind A floors unchanged.
- Preserved hard fallback behavior unless percentile history and jackknife stability pass.

## IV_RICH_MIN Treatment

`IV_RICH_MIN` is now explicitly treated as a Kind B percentile-aware gate.

Current calibration:

- Absolute legacy floor: `1.15`
- Calibrated percentile target: `0.62`
- Activation: `percentile_candidate_after_stability_pass`
- Review flag: `owner_approved_extreme_percentile`

This addresses the earlier issue where absolute IV richness interpretation had no sufficient market-context awareness. The gate does not blindly use percentile mode. It switches only when the live history window has a computed percentile threshold and the jackknife stability ratio is within the VIX-derived stability bar. Otherwise it keeps the legacy hard threshold.

## Live Decision Contract

Each wired gate now emits a `pc2_gate_basis` record containing:

- `constant`
- `gate_group`
- `gate_name`
- `gate_field`
- `gate_basis`
- `threshold_value`
- `hard_threshold_value`
- `percentile_threshold_value`
- `observed_value`
- `passed`
- `hard_passed`
- `percentile_passed`
- `counterfactual_basis`
- `counterfactual_available`
- `counterfactual_behavior_change`
- `live_percentile_authority`
- `live_behavior_change`
- `pct_target`
- `slice_key`
- `support_count`
- `stability_ratio`
- `stability_bar`
- `stability_pass`
- `fallback_reason`

Important distinction:

- `live_percentile_authority = true` means the live gate used percentile authority.
- `live_behavior_change = true` means percentile authority changed the pass/fail decision versus the legacy hard rule.

## Supabase Safety

No live Supabase queries were added.

The live helper reads only from the already-provided `ctx` history. Existing Java bridge code already merges `ml_context_percentile_history` into the `premiumHistory` shape supplied to Python, so live polling does not need a new database dependency.

## Fallback Rules

The active basis remains `hard_fallback` when any of these are missing:

- observed value
- hard threshold
- calibrated metadata
- 60-row history-derived percentile threshold
- VIX full-support stability bar
- jackknife stability pass

This means a partially populated or unstable history cannot silently loosen the app brain.
